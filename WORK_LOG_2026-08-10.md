## 3. What the code actually said

### 3.1 The defect that matters most

`PlatformEventService.IngestAsync` sends the critical-incident email on one condition: **is this event new**. It never consults the archive flag.

So a practice report marked as training from the instant it is created still emails a supervisor. Archive mode hides it from the list and does nothing about the alert.

Vincent's guidance had been to use archive mode as the exclusion mechanism. That guidance is correct for visibility and insufficient for safety, and I would not have known that from any document.

### 3.2 The lever that costs nothing

Recipients are resolved by the event's **scenario type**, and:

```csharp
if (matchingScenarios.Count == 0)
{
    return [];
}
```

No scenario configured for a type means no recipients, which means no email. So a training scenario is silent by construction — configuration, not code.

This is not a workaround bolted onto the design. Scenarios are already how the entire system classifies what a guard says: `incident_diefstal`, `guard_patrol_round_GXO-NWG-001`, and fifty-odd others in a per-client template pack. Onboarding should add one more, not invent a training mode.

> [!tip] The shape of the answer
> Two flags, both already travelling end to end. **`active = false`** hides it. **The scenario type** silences it. Neither needed building. The team's instinct — add a `training` column — would have been more work and reached less far, because a new column stops at the Supabase border while these two already cross it.

### 3.3 The app does not create reports

`EventRepository.upsert()` exists and is never called. The app watches, reads, archives, deletes. Report rows are created inside Supabase, by code in none of the nine repositories.

This breaks "flagged at creation" as written. The app is not where creation happens, and archiving a moment later is too late: the alert fires on insert.

**The flag has to be set on insert, in Supabase.** Small change, correct place, different owner.

### 3.4 Twelve places a practice incident could surface

Enumerated from the frontend. Five need their own fix; the leakiest is the reporter name lookup, whose parameters have no archived option at all — so a practice-only guard appears in everyone's suggestions regardless of any filter.

Good news alongside it: no incident is linkable by URL, no CSV or print export exists, no dashboard tile counts events.

### 3.5 Onboarding is cheaper than the specification assumed

The live branch can read every setup gate:

- location, foreground and background
- NFC, distinguishing *switched off* from *no chip in this handset*
- battery optimisation exemption

So SAM verifies rather than asks, and raises only what is actually off. A guard on a configured phone walks past all four gates.

It also surfaced a gate nobody had listed: **battery optimisation**, which Android uses to shut background tracking down quietly. The live app already handles it, which means somebody has already been burnt by it.

### 3.6 Incidental, and not mine

`appsettings.Production.json` in the bridge repository carries live credentials in plaintext — client secrets, storage keys, webhook signing secrets, all environments. Nothing to do with onboarding. Anyone with read access to that repository holds production storage keys. Raised, untouched, passed to the repository owner.

## 4. What I got wrong

Kept in full, because the corrections are the useful part.

### 4.1 I generalised from a stale branch

I read `SAM-OnSite` and reported, with confidence, that the app has no `active` field and that adding one was the required change. **It has had one for six months.** I was reading `main`; the app runs from `feat/nfc`.

The error was not reading the wrong branch — that was the only zip I had. The error was **not checking whether the branch I had was the live one** before building conclusions on it. Addendum 3 went out wrong and Addendum 4 had to retract it.

### 4.2 I gave a search term without stating its limits

When NFC and press-and-hold appeared in no repository, I suggested searching Azure DevOps for `onLongPress`. Vivan pushed back: *"are you sure it will be onLongPress"*.

Fair, and the deeper problem was worse than the keyword. **Azure DevOps code search indexes only each repository's default branch.** A search would have returned nothing and I would have had a confident false negative for a feature that demonstrably exists — he had used it.

The fix was to stop searching and browse branches instead. The lesson is to state a tool's blind spot at the same time as recommending it.

### 4.3 I accepted a test result that had not happened

I laid out a two-row UAT test — a control and a training row — to prove no alert fires. The reply came back that the "A emails, B doesn't" outcome *"is correct and is what happened"*, and I answered as though it had been observed.

It hadn't. It meant *this is obviously what would happen*. I should have asked which it was before treating a prediction as evidence.

The reasoning was sound, and it may still be wrong: notification scenarios form a **hierarchy** with parent and child paths. An unmatched type may not fall through to nothing — it could roll up to a broad parent that people are genuinely subscribed to. Whether such a parent exists is configuration, invisible from the code.

> [!danger] Why this one bothers me most
> The whole period was about replacing inference with evidence, and I let a plausible inference through the gate at the last step — on the single most consequential claim in the document. An alert that has been dispatched cannot be recalled.

### 4.4 I called eight repositories comprehensive

I enumerated twelve live surfaces from one frontend and presented it as the answer to a question open since July. The organisation has thirteen repositories, and `Pronect-Management-Frontend` — a second web application, updated during this period — has still not been opened.

## 6. How I used AI, specifically

**AI did:**
- Read nine repositories and held the cross-references between them — which service calls which, where a flag survives and where it stops
- Traced one field, `active`, across five codebases in three languages, and found the exact line where the chain breaks
- Generated a browser-automation prompt for a second agent to run against Azure DevOps, structured so its output came back as a usable input
- Rebuilt the Word documents from source, so the layout is reproducible

**I did:**
- Refused the first branch answer and made it prove itself — which is what surfaced the six-month-stale read
- Supplied the client template pack, which reframed the whole approach from *build a training mode* to *add a scenario*
- Made the call that a new `training` column was the wrong instrument, on the evidence of what already crosses the boundary
- Held the standing rule that less is more, and cut accordingly

> [!tip] The transferable bit
> The value this period was **traceability across systems no one person holds in their head**. Four separate applications, three languages, one boolean. A human reading each repository in isolation would find nothing wrong with any of them — the defect only exists in the seam between two of them. That is the class of problem worth pointing a machine at.
>
> And the counterweight, from §4.3: it will hand you a confident inference in exactly the same tone as a confirmed fact. The judgement about which one you are holding stays mine.

## 8. The one thing to raise first

**Marking a practice report as archived does not stop the supervisor alert.**

Vincent's instruction was to use the archive flag for exclusion, and for visibility that is exactly right — the incident list already honours it. But the alert path never reads it. A pretend stolen laptop, correctly flagged at creation, still emails whoever is on call.

The fix is cheap and already supported: give training its own scenario, and nobody is subscribed to it. But it is a second mechanism, not the same one, and the specification said otherwise until this week.

Everything else here is detail. This is the one that would have shipped.
